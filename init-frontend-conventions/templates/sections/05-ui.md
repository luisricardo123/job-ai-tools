## Convenciones de código

### Componentes

- Cada componente vive en su propia carpeta, con
archivos separados (`.ts`, `.html`, `.scss`, `.spec.ts`) y, si necesita exponer tipos propios, un
`{name}.types.ts` junto a los demás. 
- Los componentes en `page/` usan `export default` (requerido
por `loadComponent`).

Orden interno ESTRICTO:

```typescript
export class ExampleComponent {
  // 1. Inputs
  readonly data = input<Data>();
  readonly config = input.required<Config>();
  // 2. Outputs
  readonly itemSelected = output<Item>();
  // 3. ViewChild / ContentChild
  private readonly modal = viewChild<ModalComponent>('modal');
  // 4. Servicios inyectados
  private readonly service = inject(ExampleService);
  // 5. Constantes locales del componente
  private readonly MAX_ITEMS = 10;
  // 6. Signals de estado local
  protected readonly loading = signal<boolean>(false);
  // 7. Computed signals
  protected readonly isValid = computed(() => this.data()?.isValid ?? false);
  // 8. Lifecycle hooks
  // 9. Métodos públicos
  // 10. Métodos privados
}
```

**Visibilidad**: inputs y outputs quedan públicos — son la API real del componente, accesible por
padres y queries. Todo lo demás es `private`, salvo lo que el propio template lea (signals de
estado, computed, `viewChild` cuando el HTML lo usa directo): eso va `protected`, porque bajo AOT
el template no puede leer un miembro `private` — es error de compilación, no solo estilo.

**Los componentes hijos son tontos hasta donde se pueda.** Un componente hijo no debe
inyectar servicios de API ni de estado, no navega y no decide reglas de negocio: recibe todo lo que
muestra por input y avisa todo lo que pasa por output. Quien orquesta es la página padre —
ella inyecta los servicios, resuelve la lógica y le pasa al hijo el resultado ya masticado.

```typescript
// ❌ el hijo se busca la vida solo
export class AccountListComponent {
  private readonly service = inject(AccountService);   // no
  private readonly router = inject(Router);            // no
}

// ✅ el hijo solo pinta y avisa
export class AccountListComponent {
  readonly accounts = input.required<Account[]>();
  readonly status = input.required<ViewStatus>();
  readonly accountSelected = output<Account>();
}
```

Si un componente hijo necesita un dato que no tiene, se agrega un input; no se inyecta el servicio ahí.
La excepción son componentes de `shared/` genuinamente autónomos (p. ej. uno que consulta un
catálogo reutilizable) — y aun así, prefiere el input si es viable.

Constantes usadas solo por ese componente van ahí, en el paso 5 (arriba de los signals) — no en
`shared/constants/`. Si terminan usándose desde más de un componente, se mueven a
`shared/constants/` (ver sección "Constantes" más abajo); mismo criterio de casing.

**Toda propiedad que no se reasigna es `readonly`.** Sin excepciones.

### Formularios

En la plantilla se enlaza **siempre con `[formControl]`, nunca con `formControlName`**:

```html
<!-- ❌ --> <input formControlName="amount" />
<!-- ✅ --> <input [formControl]="form.controls.amount" />
```

`[formControl]` apunta al control real, así que el compilador valida que exista y que el tipo
calce; `formControlName` es un string suelto que solo falla en runtime si te equivocas o
renombras el campo.
